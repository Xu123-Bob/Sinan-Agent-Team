## Обзор
**Данный проект представляет собой фреймворк мультиагентной разработки стратегий и оценки их эффективности**
- Продукт совместно строит систему разработки и оценки стратегий с помощью **Rule\Rubric\LLM-to-judge**
- В проекте всего **6 агентов**: 2 агента-составителя заданий, 2 агента-арбитра, 1 агент-разведчик и 1 агент-судья
- Уровень Rule включает ограничения на бизнес-содержание, а также ограничения на **структуру вывода агентов** (чтобы гарантировать корректный вывод агентов)
- Rubric создаётся в ходе **игры 2 агентов-составителей заданий**, каждый излагает свою точку зрения, и в итоге **агент-арбитр выполняет окончательное подтверждение**
- Разработка и оценка стратегий осуществляется в ходе **обсуждения 2 агентов-разработчиков стратегий**, и в итоге **агент-арбитр также выполняет окончательное подтверждение**
- Сканирование и получение данных и профессиональных знаний выполняет **1 агент-разведчик**, который в основном сканирует `knowledge/`, `data/`, `output/`
- Генерируемые продукты включают: **план стратегии, таблицу вопросов Rubric и стенограмму обсуждения**, которые в итоге сохраняются в `knowledge/`. При итерации новых стратегий **агент-разведчик автоматически сканирует**
- Этот проект — моя работа, участвовавшая в Пекинском молодёжном хакатоне по ИИ 2026, занявшая 4-е место в оценке Alipay и рекомендованная на конкурс интеллектуальных агентов Alipay

## Ключевые особенности

- **Архитектура из 6 агентов**: Разведка / Группа составителей заданий (A+B) / Группа стратегий (A+B) / Судья, каждый выполняет свою роль |
- **Строгая изоляция контекста**: Группа составителей заданий ↔ Группа стратегий полностью изолированы; приватная память Judge никогда не утекает |
- **Общая база знаний только для чтения**: `knowledge/` доступна для чтения всем агентам, но ни один агент не может в неё писать |
- **Двойная игра в три раунда**: Группа Rubric A ⇄ B, группа стратегий A ⇄ B, каждая по три раунда игры |
- **Независимое решение Judge**: Единственный агент, видящий весь контекст, выдаёт только продукты решений |
- **Строгая валидация JSON Schema**: Вывод каждого агента обязан пройти Pydantic; при неудаче автоматически 2 повторные попытки |
- **Двойная проверка жёстких правил до и после**: Внедряются в Prompt перед генерацией, независимо проверяются после генерации; пользователь может настроить нижнюю границу |
- **Несколько Provider и Key**: Один Provider поддерживает ротацию нескольких Key; каждый агент может независимо указать модель |
- **Ввод любого пути**: Относительный / абсолютный / Windows / Linux / отдельный файл / папка; Enter для автоматического сканирования |
- **Любая бизнес-область**: Встроены e-commerce / GitHub / AtomGit / Douyin / TikTok; возможны расширение и настройка |
- **Полностью китайский CLI**: Рендеринг Typer + Rich, цветные панели, вывод процесса дебатов в реальном времени |

## Установка (выберите 1 из 3 способов)

### Способ 1: Скрипт в один клик (рекомендуется новичкам)

```bash
# Windows
scripts\install.bat

# Linux / macOS
bash scripts/install.sh
```

Скрипт автоматически проверит Python, создаст venv, установит зависимости и запустит doctor для проверки.

### Способ 2: Ручная установка (для разработчиков, знакомых с Python)

```bash
# Настоятельно рекомендуется использовать виртуальное окружение
python -m venv .venv

# Активация (выберите 1 из 3)
source .venv/bin/activate         # Linux / macOS
.venv\Scripts\activate            # Windows CMD
.venv\Scripts\Activate.ps1        # Windows PowerShell

# Установка
pip install -e .
```

> **Внимание пользователям Python 3.13+**: Если после `pip install -e .` команда `sinan` выдаёт `ModuleNotFoundError: agent.core.xxx`, используйте:
> ```bash
> pip install .
> ```
> Или запускайте напрямую через `python -m agent` (см. раздел «Запуск» ниже).

### Способ 3: Docker (чтобы избежать проблем с окружением)

```bash
docker build -t sinan .

docker run -it --rm \
  -v $(pwd)/.env:/app/.env \
  -v $(pwd)/knowledge:/app/knowledge \
  -v $(pwd)/data:/app/data \
  -v $(pwd)/outputs:/app/outputs \
  sinan
```

Полностью обходит проблемы версии Python, компиляции зависимостей и системных различий.

## База знаний

`knowledge/` — это **общая база знаний только для чтения**, доступная как справочник для всех 6 интеллектуальных агентов.

### Особенности
- **Совместное чтение**: Все агенты читают содержимое базы знаний как справочник перед генерацией
- **Запись запрещена**: Уровень кода `safe_io.safe_write` принудительно блокирует |
- **Физическое усиление**: Рекомендуется выполнить `chmod -R a-w knowledge/` (Linux/macOS) |
- **Не нарушает изоляцию**: База знаний — статический публичный справочник, совершенно не связанный с историей игры |
- **Контролируемый объём**: Усечение до 8k символов на файл и 20k символов всего, настраивается через `.env` |
- **Мультиформат**: md / txt / docx / xlsx / csv / pptx / yaml / json |

### Подходящее содержимое

- Корпоративный бренд / нормы языка
- Отраслевые стандарты / политические красные линии
- Внутренние SOP / процессные документы
- Многоразовые шаблоны стратегий
- Исторические успешные кейсы (после анонимизации)
- Финансовые знания

### Неподходящее содержимое

- Секретные ключи / пароли в открытом виде
- Приватные данные клиентов
- Крупные бинарные файлы (изображения/видео)

## Конфигурация

### Многоуровневая конфигурация (рекомендуется)

Каждый агент может независимо указать модель и key:

```env
SINAN_DEFAULT_PROVIDER=kimi/deepseek/GLM/Qwen

SINAN_RUBRIC_A_PROVIDER=kimi/deepseek/GLM/Qwen
SINAN_RUBRIC_B_PROVIDER=kimi/deepseek/GLM/Qwen
SINAN_STRATEGY_A_PROVIDER=kimi/deepseek/GLM/Qwen
SINAN_STRATEGY_B_PROVIDER=kimi/deepseek/GLM/Qwen
SINAN_JUDGE_PROVIDER=kimi/deepseek/GLM/Qwen
```

### Пул нескольких Key (ограничение скорости / несколько аккаунтов)

```env
# Через запятую
SINAN_DEEPSEEK_API_KEYS=sk-1,sk-2,sk-3

# Или с нумерацией по строкам
SINAN_DEEPSEEK_API_KEY_1=sk-1
SINAN_DEEPSEEK_API_KEY_2=sk-2
SINAN_DEEPSEEK_API_KEY_3=sk-3
```

Баннер запуска покажет `✅ x3 ротация`, и все вызовы будут автоматически распределяться по кругу (round-robin).

### Имя переменной key для каждого Provider
- DeepSeek: `SINAN_DEEPSEEK_API_KEY`
- Kimi / Moonshot: `SINAN_MOONSHOT_API_KEY`
- Qwen / Tongyi Qianwen: `SINAN_DASHSCOPE_API_KEY`
- GLM / Zhipu: `SINAN_ZHIPUAI_API_KEY`
- Ollama локально: key не требуется

### Настройка жёстких правил

Отредактируйте `configs/rules.yaml`:

```yaml
global:
  rules:
    - name: "Запрет абсолютных выражений"
      type: "forbidden"
      value: "лучший|первый|абсолютный"
      score: 20
      description: "Стратегия не должна содержать абсолютных выражений"

healthcare:
  rules:
    - name: "Не включать торговые названия рецептурных препаратов"
      type: "forbidden"
      value: "аспирин|ибупрофен"
      score: 20
```

Поддерживаемые типы правил: `keyword` / `forbidden` / `regex` / `min_length` / `schema_field`.

## Ключевые моменты архитектуры

### Гарантия изоляции контекста
```
| Агент | Видит игру Rubric | Видит игру Strategy | Видит память Judge | Видит базу знаний | Пишет в базу знаний |
|---|:---:|:---:|:---:|:---:|:---:|
| 🔍 ScoutAgent | ✗ | ✗ | ✗ | ✓ | ✗ |
| 🧩 RubricAgentA / B | ✓ (только свою группу) | ✗ | ✗ | ✓ | ✗ |
| 🎯 StrategyAgentA / B | ✗ (получает только final_rubric) | ✓ (только свою группу) | ✗ | ✓ | ✗ |
| ⚖️ JudgeAgent | ✓ | ✓ | ✓ (свою приватную) | ✓ | ✗ |
```
### Строгая валидация Schema вывода
```
| Агент | Schema вывода |
|---|---|
| Scout | `ScoutReport` |
| RubricA / B | `RubricSchema` |
| StrategyA / B | `StrategySchema` |
| Judge | `RubricDecision` / `StrategyDecision` |
```
При неудаче сообщение об ошибке автоматически возвращается LLM для самокоррекции, максимум 2 повторные попытки.

### Трёхуровневая защита жёстких правил

```
До генерации: rule_constraints внедряются в Prompt → агент активно их соблюдает
После генерации: RuleEngine.evaluate(final_strategy) → независимая проверка и оценка
При записи: safe_io.safe_write → блокирует запись в базу знаний
```

## Устранение неполадок

### Диагностика в один клик (запускать в первую очередь)

```bash
python -m agent.doctor
```

Проверяет:
- Версию Python
- Сторонние зависимости
- Целостность пакета agent (24 модуля)
- Способ установки (editable / обычная / исходный каталог)
- Тест запуска

И даёт **конкретные команды исправления** для проблем.

### Быстрый справочник по частым проблемам

#### `sinan` выдаёт `ModuleNotFoundError: No module named 'agent.core.xxx'`

**Причина**: В Python 3.13+ отображение finder при editable install неполное.

**Исправление (выберите 1 из 3)**:

```bash
# Вариант A: перейти на обычную установку
pip uninstall -y sinan-agent
pip install .

# Вариант B: использовать альтернативный способ запуска
python -m agent

# Вариант C: создать обёртку sinan.cmd в Windows
# См. TROUBLESHOOTING.md
```

#### Команда `sinan` не найдена

```bash
# Используйте альтернативный запуск
python -m agent
```

Или добавьте `Scripts\` Python в переменную окружения PATH.

#### Зависимости не устанавливаются / зависают

**Причина**: Слишком новая версия Python, некоторые пакеты ещё не адаптированы.

**Исправление**:
1. Переключиться на Python 3.12
2. Или использовать Docker: `docker build -t sinan . && docker run -it sinan`

#### `⚠ У следующих агентов отсутствует API Key`

**Причина**: В `.env` неправильно указано имя переменной key соответствующего provider.

**Частые ошибки**:

| Вы написали | Должно быть |
|---|---|
| `SINAN_KIMI_API_KEY` | `SINAN_MOONSHOT_API_KEY` |
| `SINAN_QWEN_API_KEY` | `SINAN_DASHSCOPE_API_KEY` |
| `SINAN_GLM_API_KEY` | `SINAN_ZHIPUAI_API_KEY` |

#### `Ошибка валидации Schema (после 2 повторных попыток)`

**Причина**: Нестабильный формат JSON-вывода LLM (малая модель / высокая температура).

**Исправление**: Назначить ключевым агентам более мощную модель

```env
SINAN_RUBRIC_A_PROVIDER=deepseek
SINAN_JUDGE_PROVIDER=deepseek
```

> Другие пункты устранения неполадок см. в [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md).
